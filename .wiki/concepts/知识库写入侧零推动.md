## 原则

**写入必须由用户决定**——会话蒸馏（边栏启动器）才是正规通道，模型不得自行沉淀。

## 因果链实证：是插件的 L5 把模型推去写库

```
seq=10052  插件注入「沉淀提醒」（L5）
seq=14128  模型调用 wiki_capture      ← 因果在此
seq=14253  模型接着调用 wiki_lint     ← 自检（38s）
```

那个会话共 2 条插件注入（`知识库身份` + `沉淀提醒`），**唯一一次知识库写入就紧跟在沉淀提醒之后**。`wiki_lint` 那次自检也是这条行为链的续集。

顺带排除了一个猜测：**注入体量不是耗时来源**。库身份 176 字符 + 沉淀提醒 100 字符 ≈ **200 token/会话**；真正的耗时是模型自身的调用往返（单回合 1729s ÷ 213 步 ≈ **36s/步**，而 `read` 一个本地文件 14 次全在 31–38s，`pwsh` 里 0–1 秒的条目恰好是同一条消息里批量并行的调用）。**为了省 token 去砍这几百 token 的提示是找错了对象**，真正该省的是不必要的工具调用。

## 处置

- **L5 整体移除**：`renderCaptureReminder` / `shouldRemindCapture` / `foldTurnFacts` 保留为纯函数（有用例），但**零调用点**。
- 中途一次教训：光改文案（"先问用户"）只是"劝"，模型可能仍自行写库，所以又加了**写入闸**——挂在 `tools/pre-execute`，只拦 `wiki_capture` / `wiki_ingest`（`wiki_lint` 等校验/读取不算写入）。

## 关键决策：写入闸必须默认 off

查证后发现：**UI 蒸馏走的就是 `wiki_ingest`**——与模型自行写库**同一个工具名**。钩子看不到"这次调用是谁授权的"，因此**任何默认开启的写入闸都会挡住用户自己点的蒸馏**。

结论：闸门代码保留、**默认 `off`**，改为显式 opt-in（`KNJ_OBSIDIAN_WRITE_GATE=ask|block`）。理由必须写进文档，否则下次有人会好心把它改回默认开。

诚实边界（不要把它当成强约束卖）：钩子无法机器验证"你真的同意了"，它挡的是**未经询问就写**，挡不住模型自问自答式地"问了一句"再写。要机器可验证的用户决定，需走宿主审批服务（`tools/pre-execute` 返回 `{kind:'ask'}`，见 [[dsh-插件宿主接口契约]]），代价是审批提示被禁用时这类写入会被直接拒。

## 最终行为

**读取侧照旧主动**（L0 库身份 / L1 两档 / L3 复发，见 [[知识库读取触发层设计]]），**写入侧零推动**——不提醒、不拦截，沉淀只由用户点 UI 蒸馏触发。
